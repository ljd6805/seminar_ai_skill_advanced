# Seminar Synopsis — SKILL 심화 (이론편: 기법 카탈로그)

> **버전**: v0.1 (2026-08-21)
> **상태**: 논리 구조 확정, 슬라이드 초안 v0.1 작성 완료
> **이 문서의 용도**: 슬라이드 작성의 기준 문서. 슬라이드의 모든 장은 이 문서의 장 구조를 따른다. 시놉시스와 슬라이드가 어긋나면 시놉시스를 먼저 갱신한다.

## 1. 세미나 메타 정보

| 항목 | 내용 |
|---|---|
| 시리즈 | AI Agent 세미나 4편 (1편 seminar_ai_agent · 2편 seminar_ai_skill_quest · 3편 seminar_ai_hook_harness_slide) |
| 이번 편 구성 | 이론편(본 문서) + 실습편(Skill Quest 심화 시즌, **방식 미정 — 별도 기획**) |
| 발표 시간 | 90분 목표 (발표 75분 + Q&A 15분) |
| 청중 | 팀 엔지니어 전원 — 2편(Skill Quest)으로 스킬 기초를 실습했고, 3편으로 Hook/Harness 개념을 접한 상태 |
| 환경 전제 | 사내 LLM은 **컨텍스트 256k** — 이 제약을 세미나 전체의 설계 조건으로 삼는다 |
| 도구 기준 | opencode (`.opencode/skills/<이름>/SKILL.md`) — 원리는 도구 중립으로 서술 |
| 예시 수준 | 팀 공용 소재(리그레션 로그, 테스트 리포트, 리뷰 정리 등) — 2편 실습 리포의 데이터(`regression.log`, `test_results.csv`)를 재사용해 실습 연계를 예비한다 |

## 2. 핵심 메시지 (한 문장)

> **스킬 하나는 절차를 담고, 스킬 시스템은 한계를 설계한다 — 256k는 벽이 아니라 설계 조건이다.**

부제: 컨텍스트에는 결론만, 스킬 사이에는 계약을, 완료에는 증거를.

## 3. 전개 원칙 — 이 세션이 지키는 네 가지 규칙

1. **기법은 문제 없이 등장하지 않는다.** 모든 기법 카드는 문제제기로 시작한다. 도입부에서 세 가지 문제를 목격시키고, 파트가 그 문제의 답이 된다.
2. **모든 기법은 같은 카드 한 장으로 읽는다.** 고정 7단 구조 — ① 기법 이름 → ② 문제제기 → ③ 기법설명 → ④ 예제 → ⑤ 스킬구성 → ⑥ 문제극복 원리 → ⑦ 스킬효과. 카드의 지리(배치·색)를 고정해 14장을 근육 기억으로 읽게 한다.
3. **색 언어는 시리즈를 상속한다.** 보라=Agent/절차 · 청보라=Skill 구성 · 민트=효과/자원 · 코랄=문제/검증 · 앰버=원리/사람. 검증 파트는 3편 Harness의 개념(Validation·Record·Gate)과 명시적으로 연결한다.
4. **실습은 예고만, 확정 사항만 말한다.** 실습 방식은 미정이므로 "기존 Skill Quest 리포 위에 심화 미션 트랙이 얹힌다"는 방향만 예고한다.

## 4. 전체 전개 구조

```text
잘 만든 스킬이 막히는 세 장면 (목격)
        ↓
문제 3 + 1 도출
  ① 컨텍스트가 모자라다 (256k)      → PART 1 · 컨텍스트 절약술 (기법 ①~⑤)
  ② 프로세스가 사람 손에 있다        → PART 2 · 스킬 연계술   (기법 ⑥~⑨)
  ③ "완료"를 믿을 수 없다           → PART 3 · 검증·리뷰 하네스 (기법 ⑩~⑬)
  ④ 팀에 어떻게 퍼뜨리나            → PART 4 · 확산 (기법 ⑭)
        ↓
기법 선택 지도 (문제 → 기법 결정 흐름)
        ↓
종합 사례 (한 업무에 기법 7개 겹쳐 쓰기 — 주간 리그레션 리포트)
        ↓
실습 예고 (Skill Quest 심화 시즌) → 마무리 세 문장
```

## 5. 기법 카탈로그 (14)

### PART 1 · 컨텍스트 절약술 — "컨텍스트에는 결론만 들여보낸다"

| # | 기법 | 문제 | 극복 원리 | 한 줄 |
|---|---|---|---|---|
| ① | 레퍼런스 계층화 (Progressive Disclosure) | 지식 전부를 본문에 넣으면 발동만 해도 수만 토큰 | 상주는 description 한 줄뿐, 지식은 조건부 로드 | 목차만 상주, 지식은 문 뒤에 |
| ② | 스크립트 위임 (Script Offloading) | 50만 줄 로그는 안 들어가고, 세면 틀린다 | 집계는 컨텍스트 밖 코드가, 판단만 모델이 | 세는 일은 코드가, 뜻은 모델이 |
| ③ | 외부 기억 (External Memory) | 긴 작업은 컴팩션·세션 종료로 기억을 잃는다 | 기억을 대화(휘발)에서 파일(영속)로 이동 | 대화는 흘러가고 파일은 남는다 |
| ④ | 지도 우선 탐색 (Map-first Navigation) | 통째 읽기는 대형 리포에서 컨텍스트 파산 | 소비가 리포 크기가 아닌 질문 크기에 비례 | 읽기는 검색의 결과여야 한다 |
| ⑤ | 분업 요약 (Fan-out & Summarize) | 아무리 아껴도 한 컨텍스트에 안 들어가는 일 | 총량을 1×256k → N×256k로 확장, 회수는 요약만 | 쪼개면 컨텍스트는 곱해진다 |

### PART 2 · 스킬 연계술 — "부품이 되려면 계약이 필요하다"

| # | 기법 | 문제 | 극복 원리 | 한 줄 |
|---|---|---|---|---|
| ⑥ | 산출물 계약 (Artifact Contract) | 스킬 결과가 대화에 흘러가 다음 스킬이 못 받는다 | 전달을 대화(비정형)에서 약속된 파일(정형)로 | 계약이 있어야 부품이 된다 |
| ⑦ | 파이프라인 스킬 (Pipeline Orchestrator) | 다단계 업무를 사람이 매 단계 지휘 | 시니어의 암묵적 순서를 명시적 자산으로 | 프로세스도 스킬이다 |
| ⑧ | 라우터 스킬 (Router Skill) | 스킬 20개 — 오발동·미발동·발견 실패 | 발동 판단을 description 경쟁에서 분류표로 승격 | 전문가가 많을수록 접수 창구 |
| ⑨ | 게이트 체크 (Stage Gate) | 부실 산출물이 다음 단계로 흘러 오염 증폭 | 결함을 가장 싼 단계에서 차단 (3편 게이트 개념) | 게이트가 있어야 흐름을 믿는다 |

### PART 3 · 검증·리뷰 하네스 — "'됐습니다'를 '증명됐습니다'로"

| # | 기법 | 문제 | 극복 원리 | 한 줄 |
|---|---|---|---|---|
| ⑩ | 자가 리뷰 루프 (Self-Review Loop) | 작성자 모드는 자기 결과에 관대 | 생성 프레임과 비판 프레임의 분리 | 같은 모델, 다른 프레임 |
| ⑪ | 반박 검증 (Adversarial Check) | 리뷰어 모드도 관대한 통과를 남발 (확증 편향) | 반증주의의 절차화 — 반례 하나가 결정적 | 반박에서 살아남은 결론만 결론 |
| ⑫ | 기계 채점 하네스 (Script-Judged Gate) | "됐다고 말하는 것"과 "된 것"의 간극 | 판정을 확률(LLM)에서 결정(코드)으로 — 3편 Validation 루프의 스킬 내장 | 말이 아니라 채점으로 통과 |
| ⑬ | 증거 기반 완료 (Evidence-based Done) | 완료 한 줄 — 사람이 처음부터 재확인 | 완료의 정의를 주장에서 검증 가능한 기록으로 — 3편 Record의 산출물 적용 | 증거가 없으면 완료가 아니다 |

### PART 4 · 확산

| # | 기법 | 문제 | 극복 원리 | 한 줄 |
|---|---|---|---|---|
| ⑭ | 스킬 팩토리 (Meta-skill) | 팀원마다 SKILL.md 품질이 제각각 | 모범 사례를 문서가 아니라 실행되는 생성기로 배포 | 표준은 기본값으로 배포한다 |

## 8. 실습 연계 계획 (미정 사항 명시)

- **확정**: 기존 `seminar_ai_skill_quest` 리포(데이터·채점기·보드)를 기반으로 심화 미션 트랙을 얹는다. 이론편 카드의 ⑤스킬구성이 실습 미션의 골격이 된다.
- **후보 미션**: 스크립트 위임(②) · 산출물 계약+파이프라인(⑥⑦) · 채점 루프(⑫) · 반박 검증(⑪).
- **미정**: 미션 수, 레벨 체계(기존 Lv.8+ 확장 vs 별도 시즌 보드), 일정. 확정 전까지 슬라이드에는 방향만 예고한다.

## 9. 결정 기록

| 결정 | 이유 |
|---|---|
| 14기법을 고정 7단 카드로 통일 | 요청된 서술 구조(이름→문제→설명→예제→구성→원리→효과)를 시각 포맷으로 승격 — 장수가 많아도 읽는 비용이 늘지 않게 |
| 256k를 별도 장(5장)으로 독립 | 사내 환경의 실제 제약 — PART 1 전체의 문제의식이므로 도입에서 체감시킨다 |
| 검증 파트를 "하네스"로 명명 | 3편과의 연속성 — Validation·Record·Gate 개념을 스킬 안으로 가져온다는 메시지 |
| 예시 소재를 2편 실습 리포와 통일 | 실습 세미나(방식 미정)와의 연계 비용 최소화 |
| 서브에이전트는 "새 세션 위임"과 병기 | 사내 opencode 버전·설정에 따라 기능 편차 가능 — 파일 경유 방식은 어디서나 동작 |
