체험하는 법 (공통)

순서

  1. case 의 before/(또는 after/)를 프로젝트 루트로 스킬 도구(opencode 등)를 연다.
  2. 카드에 준비 태그(노랑)가 있으면 그 명령을 먼저 실행한다 — 일부 case 는 준비 과정이 필요하다 (예: case02 로그 생성, case08 시드 복사).
  3. 이어서 요청 문장(파랑 태그)을 그대로 입력한다.
  4. Before → After 순서로 같은 요청을 넣고 차이를 관찰한다.
  5. 스크립트 있는 case02·case08·case12 는 에이전트 없이 스크립트만 돌려도 핵심이 보인다.
  6. 모든 데이터는 before/·after/ 안에 있다 — 폴더 하나만 열면 자립적으로 돈다.
  7. 발동·행동은 모델의 확률적 판단이라 회차마다 다를 수 있다 — 장면 재현이 아니라 스킬 구조의 차이를 보는 것이 목적.
  8. 이 문서는 시험이 아니라 경험과 케이스 스터디를 위한 것이다 — 각 카드의 SKILL.md 본문 비교와 심은 정답을 먼저 읽고 시작해도 좋다.
  9. 일부 before 스킬(case02·case04·case12)에는 “직접 읽고 직접 센다 · 스크립트 금지” 같은 재현 장치가 들어 있다 — 요즘 모델은 시키지 않아도 알아서 코드·검색으로 우회하는데, 그 우회가 바로 해당 기법이기 때문이다.

폴더 구조 · 초기화

caseNN-<기법>/
├─ README.md            ← 상세 시나리오
├─ before/
│  ├─ .opencode/skills/…/SKILL.md   ← 문제의 스킬
│  └─ (데이터: work/ logs/ src/ …)
└─ after/
   ├─ .opencode/skills/…/SKILL.md   ← 해결된 스킬
   └─ (+ references/ scripts/ assets/)

# Convention Review

## 절차
1. diff에서 파일 유형·키워드만 훑는다. (전체 정독 금지)
2. 해당하는 규칙 파일**만** 골라 읽는다:
   - 이름·구조 지적 필요        → `references/naming.md`
   - try/except·오류 코드       → `references/error-handling.md`
   - thread·mutex·lock·async    → `references/concurrency.md`
3. 읽은 규칙의 조항 번호를 근거로 지적한다. (예: concurrency §3.1)
4. 읽지 않은 규칙으로는 지적하지 않는다.

## 금지
- `references/` 전체를 한 번에 읽는 행위
- 규칙 원문의 본문 복사 (조항 번호와 한 줄 요지만 인용)

## 출력
- 지적 목록: `[조항] 파일:줄 — 위반 내용 (1줄)` 형식
- 마지막 줄에 "읽은 규칙 파일: <목록>" 을 보고한다.

# API Migration

## 절차
1. 시작할 때 `output/state.md` 가 있으면 **먼저 읽고 이어서** 한다.
   없으면 `assets/state-template.md` 를 복사해 만든다.
2. 이번에 다룰 모듈 하나를 정하고, 규칙(state.md 상단)을 확인한다.
3. 모듈을 v2 규칙으로 수정한다. (아래 "v2 규칙" 참조)
4. 끝나는 즉시 state.md 를 갱신한다:
   - 해당 줄 `[ ]` → `[x]`
   - 특이 사항은 "메모" 절에 1줄
5. 대화가 길어지면 **대화가 아니라 state.md 를 기준**으로 삼는다.

## v2 규칙
- import: `from legacy.http import client, LegacyError` → `from api.http import client, ApiError`
- 호출: `client.call(path, body)` → `client.request("POST", path, json=body)`
- 경로: `/v1/...` → `/v2/...`
- 응답: `resp.data` → `resp.json()["data"]`
- 예외: `LegacyError` → `ApiError` 로 캐치 변경

## 금지
- state.md 갱신 없이 다음 모듈로 넘어가는 행위
- "아까 정한 규칙"처럼 대화 기억에 기대는 표현

## state.md 형식 (assets/state-template.md)
규칙: v2 통일 · [x] 01 · … · [ ] 40 · 메모: 03 API 변경 확인

# Repo Scout

## 절차 — 넓게 → 좁게 → 깊게
1. `tree -L 2` (또는 파일 목록)으로 구조만 파악한다. (내용 열람 금지)
2. `grep -rn "<심볼>"` 로 후보 위치를 찾는다.
   - 심볼을 모르면: 요청의 명사로 grep → 후보 확보
3. 후보 파일은 해당 함수 **±50줄만** 읽는다.
4. 부족하면 호출부를 grep 으로 따라가며 2~3을 반복한다.
5. 근거는 `파일경로:줄번호` 형식으로 남긴다.

## 금지
- 폴더를 순회하며 파일 전체를 읽는 행위
- 1,000줄 넘는 파일의 통째 읽기 (필요 범위만)

# PR 설명 리뷰 체크리스트 (팀 공유)

리뷰어 역할로 아래 항목만 본다. 통과 근거가 아니라 **결함**을 찾는다.

- #1 제목이 "무엇을/왜"를 한 줄로 말하는가
- #2 **테스트 영향**이 적혀 있는가 (추가/변경된 테스트, 수동 검증 절차)
- #3 호환성/마이그레이션 영향(설정·스키마·API 변경)이 명시됐는가
- #4 관련 이슈/티켓 링크가 있는가
- #5 **롤백 계획**이 있는가 (되돌리는 법)
- #6 리뷰어를 위한 확인 포인트(무엇을 봐야 하나)가 있는가
- #7 **과장·모호 표현**이 없는가 ("완벽히", "아마", "약간", "등등")

# Refute Check — 반박 검증 스킬

## 절차 (결론 검증 요청 시)
1. 검증할 결론을 한 문장으로 적는다.
2. **입장 전환 — "이 결론은 틀렸다"** 를 전제로, 반례를 3가지 경로에서 찾는다:
   - 시간 반박 — 원인 시점 **이전**에도 증상이 있었나
     (예: `grep -E "2026-08-1[012]" logs/service.log | grep ERROR` — 배포 전 로그)
   - 사례 반박 — 조건이 같은데 증상 없는 곳은
   - 대안 반박 — 같은 증상을 내는 다른 원인 후보는
3. 반례 발견 → **결론 기각**. 근거(명령·결과)를 첨부해 보고한다.
4. 3경로 모두 실패 → "반박 3회 실패"를 명시하고 채택한다.

## 기록
- 시도한 반박 경로·명령·결과를 보고에 그대로 남긴다.
- 가능하면 **새 세션**에서 실행한다. (작성 편향 차단)

# Release Check

## 출력 규칙
- **"완료" 선언은 증거표가 채워진 경우에만** 허용한다.
- 증거표 각 행 (assets/evidence-form.md):
  `점검 항목 | 실행한 명령 | 출력 원문(3줄 이내) | 판정(PASS/FAIL/미실행)`
- 실행하지 못한 항목은 판정을 `미실행` + 사유로 남긴다. (빈칸·추정 금지)
- 증거가 없는 문장은 리포트에 쓰지 않는다.

## 점검 항목 (env/ 기준 5항목 — 실제 사건은 8항목)
1. 헬스체크: `cat env/health.txt`
2. 디스크 여유: `cat env/disk.txt`
3. 백업 존재: `ls env/backups/`
4. DB 마이그레이션 준비: `cat env/migrate_check.txt` (권한 오류가 심겨 있음 → 미실행 처리)
5. 설정 검증: `cat env/config_check.txt`

## 사람의 확인
- 증거표만 훑고, "미실행"·"FAIL" 행만 조치 대상으로 넘긴다.
