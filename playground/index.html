SKILL 심화 세미나 · 부속물

playground 체험 가이드

이론편 13개 사건을 직접 손으로 돌려보기 위한 미니 워크스페이스 모음. case마다 before/(문제의 스킬)와 after/(해결된 스킬)가 나란히 있고, 같은 요청을 양쪽에 넣어 차이를 관찰한다.

⚠ 실습편(Skill Quest 심화 시즌)과는 별개. 시놉시스 §8의 실습 연계 계획과 무관한, 발표자 개인 체험용 비공식 부속물이다.
사용법 PART 1 · 절약술 ①~⑤ PART 2 · 연계술 ⑥~⑨ PART 3 · 하네스 ⑩~⑬ 스크립트 빠른 확인

체험하는 법 (공통)

순서

  1. case 의 before/(또는 after/)를 프로젝트 루트로 스킬 도구(opencode 등)를 연다.
  2. 아래 카드의 요청 문장을 그대로 입력한다.
  3. Before → After 순서로 같은 요청을 넣고 차이를 관찰한다.
  4. 스크립트 있는 case(②⑧⑫)는 에이전트 없이 스크립트만 돌려도 핵심이 보인다.
  5. 모든 데이터는 before/·after/ 안에 있다 — 폴더 하나만 열면 자립적으로 돈다.
  6. 발동·행동은 모델의 확률적 판단이라 회차마다 다를 수 있다 — 장면 재현이 아니라 스킬 구조의 차이를 보는 것이 목적.

폴더 구조 · 초기화

caseNN-<기법>/
├─ README.md            ← 상세 시나리오
├─ before/
│  ├─ .opencode/skills/…/SKILL.md   ← 문제의 스킬
│  └─ (데이터: work/ logs/ src/ …)
└─ after/
   ├─ .opencode/skills/…/SKILL.md   ← 해결된 스킬
   └─ (+ references/ scripts/ assets/)

# 체험 후 원상복구 (확인 프롬프트 있음)
bash playground/reset.sh

PART 1 · 컨텍스트 절약술 — 컨텍스트에는 결론만

사내 LLM의 256k 컨텍스트를 설계 조건으로 삼는 다섯 사건. 원본은 밖에 두고, 결론만 들여보낸다.

①

레퍼런스 계층화 Progressive Disclosure

목차만 싣고, 지식은 문 뒤에 — 비용이 보유량이 아니라 사용량에 비례.

case01-progressive-disclosure/
요청work/changes.diff 컨벤션 리뷰해줘

BEFORE 관찰

규칙 3편(네이밍·예외·동시성)이 SKILL.md 본문에 통째 — 발동 순간 전부 로드된다. 이번 diff에 필요한 건 동시성 한 편뿐.

AFTER 관찰

SKILL.md는 목차 역할만. diff에서 thread/lock 감지 → references/concurrency.md만 읽고 조항 번호(§)로 지적. naming·error-handling은 끝까지 읽히지 않는다.

심은 정답 — diff의 동시성 위반 3건: 락 안 sleep(§1.1) · 무락 카운터 증가(§3.1) · 종료 설계 없는 스레드(§5.1)

②

스크립트 위임 Script Offloading

세는 일은 코드가, 뜻을 읽는 일은 모델이.

case02-script-offloading/
준비python3 tools/make_log.py --lines 50000
요청지난밤 logs/regression.log 원인 분석해줘

BEFORE 관찰

로그를 직접 READ — 일부만 읽고 추정하거나, 셀 때마다 건수가 달라진다(세기는 확률 모델의 약점).

AFTER 관찰

읽지 않고 scripts/digest.py 실행 → 요약 30줄만 근거로 사용. 수치는 스크립트 값 그대로 인용.

심은 정답 — AssertionError 1,842 · TimeoutError 317 · 첫 급증 02:14 (슬라이드와 동일 수치)

③

외부 기억 External Memory

대화는 흘러가고, 파일은 남는다.

case03-external-memory/
Beforesrc/ 모듈들을 전부 v2 API로 통일해줘 → 몇 개 진행 후 새 세션에서 이어서 해줘
After빈 컨텍스트의 새 세션에서 곧장 이어서 해줘

BEFORE 관찰

기억이 대화에만 — 세션이 끊기면 무엇을 하던 작업인지, 규칙이 v2였는지 전부 증발한다.

AFTER 관찰

after/에는 output/state.md가 03에서 끊긴 상태로 들어 있다. state.md를 먼저 읽고 03부터 v2로 재개, 끝나는 즉시 [x]와 메모 1줄 갱신.

포인트 — 지난 대화 필요량 0줄. state.md는 인수인계 문서로도 그대로 읽힌다.

④

지도 우선 탐색 Map-first Navigation

읽기는 검색의 결과여야 한다.

case04-map-first/
요청repo/ 에서 결제 검증이 어디서 어떻게 도는지 설명해줘

BEFORE 관찰

"관련 파일을 읽는다"뿐 — 1만 5천 줄 repo에서 큰 잡음 파일부터 통째로 읽다 컨텍스트가 부푼다.

AFTER 관찰

구조 파악 → grep -rn validatePayment → 해당 함수 ±50줄만 READ → 파일:줄 근거 + 읽은 총량 보고.

심은 정답 — repo/src/pay/validate.py의 validatePayment: 요청 → 한도 검사 → 승인 큐

⑤

분업 요약 Fan-out & Summarize

쪼개면 컨텍스트는 곱해진다 — 유일한 총량 확장 기법.

case05-fanout-summarize/
요청modules/ 전부 보안 점검해줘

BEFORE 관찰

한 세션이 모듈 6개의 코드+결과를 전부 떠안는다 — 늘릴수록 앞 결과가 요약으로 뭉개진다.

AFTER 관찰

plan.md로 분할 → 모듈마다 서브에이전트/새 세션에 위임 → 10줄 양식 보고만 회수 → 부모는 보고 파일만 읽고 종합. 코드 원문은 돌아오지 않는다.

심은 정답 — 취약점 6종: MD5+정적솔트 · SQL 인젝션 · path traversal · shell=True · 예측 가능 난수 · 하드코딩 자격증명

PART 2 · 스킬 연계술 — 스킬은 대화가 아니라 파일로 협업한다

하나의 장애 대응 프로세스(수집→분석→초안→검증)를 네 사건으로 이어 완성하는 연작. ⑥무엇을 주고받나 · ⑦순서는 · ⑧믿어도 되나 · ⑨누가 나서나.

⑥

산출물 약속 Artifact Contract

약속이 있어야 부품이 된다 — 경로·형식·버전.

case06-artifact-contract/
요청 1logs/incident.log 요약해줘
요청 2방금 요약으로 장애 리포트 만들어줘

BEFORE 관찰

요약이 화면에만 남는다 — 리포트 스킬이 "요약이 어디 있죠?" 사람이 복붙하면 구버전 사고. 함수로 치면 return 없이 print만 한 꼴.

AFTER 관찰

생산자는 output/digest.md (3섹션 + DIGEST-VERSION: 1)로 저장, 소비자는 버전 확인 후 그것만 근거로. 버전 줄을 지우고 다시 요청하면 거부하는지 실험해 보라.

포인트 — 이 약속의 책임은 전달까지. 내용 품질은 ⑧의 몫.

⑦

파이프라인 스킬 Pipeline Orchestrator

프로세스도 스킬이다 — 순서를 아는 스킬은 하나면 된다.

case07-pipeline/
요청장애 대응 시작해줘

BEFORE 관찰

부품 4개뿐, 조립 설명서 없음 — 분석을 건너뛰고 리포트를 시키면 "원인 미상" 리포트가 그대로 발행된다.

AFTER 관찰

지휘자 incident-flow가 단계표대로 1→4 자동 진행, 단계마다 산출물 경로 한 줄 보고. digest·analysis만 남기고 재시작하면 3단계부터 재개되는지 확인(③의 원리).

포인트 — 단계를 잇는 화살표가 ⑥의 산출물 약속이다.

⑧

게이트 체크 Stage Gate

약속이 형식을 본다면, 게이트는 내용을 본다.

case08-stage-gate/
준비cp output/analysis.bad.md output/analysis.md
요청장애 리포트 써줘

BEFORE 관찰

입력을 검사 없이 신뢰 — 재현 절차가 빈 분석을 그대로 근거로 삼거나 지어낸다.

AFTER 관찰

도입부에서 gate.py 실행 → GATE FAIL(부족 항목 명시)로 멈추고 반려. good으로 바꾸면 PASS 후 진행, PASS 로그를 리포트 끝에 첨부.

심은 정답 — analysis.bad.md → FAIL(재현 절차·영향 범위) · analysis.good.md → PASS 3/3. 게이트는 모든 연결이 아니라 부실이 비싸지는 길목에만.

⑨

라우터 스킬 Router Skill

전문가가 많을수록 접수 창구가 필요하다.

case09-router/
요청이 로그 좀 봐줘 · 리뷰 코멘트 정리해줘 · 그… 지난주 그거 정리해줘

BEFORE 관찰

발동이 description 유사도 경쟁 — "로그"가 겹쳐 pdf-export 오발동, 한글 표현이 없어 review-summary 미발동.

AFTER 관찰

qa-desk 접수 창구가 분류표로 배정. 모호한 요청엔 짐작 대신 후보 2개를 제시하고 질문. 전문 스킬 description은 좁고 정확하게.

포인트 — 창구는 넓게, 전문 스킬은 좁게. 겹침도 빈틈도 사라진다.

PART 3 · 검증·리뷰 하네스 — "됐습니다"를 "증명됐습니다"로

같은 모델이라도 프레임·방향·도구·형식을 바꾸면 검증이 된다. 네 겹의 그물.

⑩

자가 리뷰 루프 Self-Review Loop

같은 모델, 다른 프레임 — 혼자서 하는 페어 리뷰.

case10-self-review/
요청work/changes.diff 로 PR 설명 써줘 (Before에선 이어서 괜찮아? 빠진 거 없어?)

BEFORE 관찰

검토 단계가 없다 — "괜찮아?"에 작성 프레임 그대로 "잘 정리되어 있습니다".

AFTER 관찰

초안 → "지금부터 리뷰어다" 역할 전환 + 체크리스트 항목별 결함만 지적(#2 테스트 영향·#5 롤백·#7 과장 표현) → 반영 → 지적 0건까지(최대 2회) → 제출.

참고 — work/draft.weak.md 는 과장·모호 표현을 일부러 심은 초안. 체크리스트 리뷰로 넣어 보라.

⑪

반박 검증 Adversarial Check

반박에서 살아남은 결론만 결론이다.

case11-adversarial/
Beforelogs/service.log 와 data/deploy-history.md 로 장애 원인 분석해줘
After"원인은 8/12 배포" 결론을 반박 검증해줘

BEFORE 관찰

지지 증거만 수집하는 절차 — 배포(8/12 13:00) 직후 오류 폭증(196건)에 끌려 "배포 탓" 결론으로 기운다.

AFTER 관찰

"이 결론은 틀렸다" 전제로 시간·사례·대안 3경로 반박 → 8/10(배포 전) 오류 발견 → 결론 기각 → 인증서 만료로 정정, 반박 기록 첨부.

심은 정답 — 8/10·11(배포 전)에 이미 CertificateError+Timeout 44건. 실제 원인은 인증서 만료.

⑫

기계 채점 하네스 Script-Judged Gate

말로 통과하지 말고, 채점으로 통과하라.

case12-script-judged/
요청data/test_results.csv 로 주간 테스트 리포트 써줘

BEFORE 관찰

"스스로 한 번 검토" — 합계 불일치·섹션 누락 같은 결정적 실수를 말(확률적 도구)로 검사해 놓친다.

AFTER 관찰

validate.py 채점 → FAIL 항목 수정 → PASS까지 루프(≤5회) → PASS 로그 원문을 리포트 끝에 첨부. 사람은 검산기가 아니라 PASS 로그만 확인.

심은 정답 — 전체 17 = PASS 12 + FAIL 3 + SKIP 2. SKIP을 빠뜨리면 합계 불일치로 FAIL.

⑬

증거 기반 완료 Evidence-based Done

증거가 없으면 완료가 아니다 — 말 대신 영수증.

case13-evidence-done/
요청env/ 기준으로 배포 전 점검해줘

BEFORE 관찰

"점검 완료 — 이상 없습니다" 한 줄 — 실행 실패한 항목이 낙관적으로 뭉개져도 알 방법이 없다.

AFTER 관찰

증거표 의무: 행마다 실행한 명령 + 출력 원문 + 판정. 4번(DB 준비)은 권한 오류라 "미실행" + 사유로 정직하게 남는다. 사람은 미실행/FAIL 행만 조치.

심은 정답 — env/migrate_check.txt 에 권한 오류(errno 13). "미실행" 표기가 정답 — 미실행은 숨길 일이 아니라 정보다.

스크립트만 빠르게 확인

에이전트 없이도 ②⑧⑫의 핵심 장치를 30초 만에 확인할 수 있다.
